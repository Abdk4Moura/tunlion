## Root cause

`devices forget` (`cli/src/fleet_support.rs:346-378`) writes `revoked-keys.json` first (`record_key_revocation_at`, line 361), then revokes grants, then removes the record from `devices.json` (line 377). That order is deliberate: revocation-first leaves no window in which fleet-hello re-admits the key.

The running daemon sweeps on a snapshot of BOTH files (`cli/src/revocation_live.rs:36-50`, polled every ~2s at `crates/filament-peerloop/src/recv/dispatch.rs:3394`). A poll that lands after the key block is written but before `devices.json` shrinks sees:

* `prune_to_store` removes no secret (the record, and its secret, are still there), and
* `key_listed(b)` is already true.

The sweep at `dispatch.rs:3450-3466` then promoted the cut to `Code::CertRevoked` ("device revoked"). A poll after both writes prunes the secret and the peer hears "not recognized". That is the F1 flake (`cli/tests/daemon-path-gates.sh:225`): a few milliseconds of write timing decide the words.

Two more holes, both deterministic:

* A fleet-only link (no pair secret on the acceptor) has `facts.secret == None`, so `secret_gone` was always false and "device revoked" came back every time. `sibling_link_must_close` also uses `device_cert_revoked`, which folds in the forget block, so a FleetSibling link was cut as revoked regardless of the secret.
* Two further paths asked `cert_revoked_for`, which also folds in the forget block: the 5 s live re-check (`cli/src/identity_state.rs:458-468`, used by the exec, pty, forward and mount loops) and the shell-class admission classifier (`Refusal::from_shell_gate`). Both could answer "device revoked" for a forget.

## Semantics

1. `devices forget` is one event in the peer's words: "not recognized here (it was forgotten, or was never paired)", `Code::Unrecognized`, wire `not-recognized`, exit 4. Timing, link kind (pair-proven or fleet-only), the presence of a live fleet certificate, and admission versus mid-session do not change it.
2. `device revoked` (`Code::CertRevoked`) stays reserved for an in-place revocation where the record is kept (`devices revoke`, `demote --to cut`), and for a sibling the owner's signed roster delisted or whose certificate expired. A withdrawn grant is still `Code::Revoked`.
3. Provenance: `record_key_revocation_at` has exactly one production caller, `forget_device` (`cli/src/fleet_support.rs:361`). Re-add (`cli/src/pair_cmd.rs:1479`) and `promote` (`cli/src/ladder.rs:373`) lift the block. No revoke, demote or expiry path writes it. Open #632 does not touch `revoked-keys.json`, `fleet_support.rs`, `identity_state.rs` or the shared `LiveCutCause`.
4. Revocation-first ordering is unchanged.

## Changes

* New pure `link_cut_reason(secret_forgotten, key_on_forget_block)` in `crates/filament-peerloop/src/recv/revocation.rs`: forgotten when either signal is set, revoked otherwise.
* The sweep (`recv/dispatch.rs`) uses it for the `link-revoked` frame and no longer promotes a forget-block key to `CertRevoked`.
* `live_session_cut` (`cli/src/identity_state.rs`) asks the forget block first and returns a new `LiveCut::Forgotten`, whose reason is the open refusal's own wording. `LiveCutCause::Forgotten` added; the exec close carries the typed code; pty, forward and mount logs name the cause; the core host follows the same precedence.
* Admission: new defaulted `HostServices::cert_forgotten_for` (the block only, separate from `cert_revoked_for`), and `Refusal::from_shell_gate` asks it first. The exec-open, pty-open and shell-bootstrap paths pass it, so a forgotten key reads "not recognized" even while the record is still present. Denials are unchanged, only the words; `ShellGateInputs` and its matrix are untouched.
* Provenance invariant documented where the list is defined and written: an entry means FORGOTTEN, `forget_device` is the only writer, and a future second-purpose writer must carry its own reason rather than reuse the list.

## Residual

There is no known remaining path that answers "device revoked" for a forget: the sweep, the live re-check and admission all consult the block first, and the admission change closes the few-millisecond new-open window. `cert_revoked_for` still folds the block in on purpose (a forgotten key must not pass fleet-hello), so any future refusal site that uses it directly must consult `cert_forgotten_for` first; the provenance comment on `KEY_REVOCATIONS_FILE` says so.
